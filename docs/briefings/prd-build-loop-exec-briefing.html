02 / The problem

AI 能写，不等于项目能交

需求未推敲就开写

PRD 有洞时，Agent 仍会自信交付错误功能。

上下文越写越脏

一次做太多任务，质量与可追溯性迅速下降。

完成定义薄弱

勾完任务不等于可上线，缺模块验收与回归门。

人被困在循环里

要么全程盯盘，要么完全失控，缺少环上管控。

05 / Two tracks

绿场新品与棕地逆向，同一套交付操作系统

Greenfield

新想法 → PRD → 实现

/prd-author → /prd-grill → /prd-build-loop

Brownfield

老代码 → As-Is → 改造

/prd-reverse → 表征基线 → To-Be / 迁移 → /prd-build-loop

As-Is 只证明“现在是什么”，不能直接当作改造 backlog。

06 / Capability map

谁负责想清楚，谁负责做出来

  • prd-author生成想法拷问后合成模块化 docs/prd
  • prd-reverse逆向老代码还原 As-Is PRD 与忠实度签核
  • prd-grill挑战门成品 PRD 再压测，未过门不准写
  • prd-build-loop主编排拆计划并驱动循环实现
  • ralph-*执行器脚手架、单任务、外层续跑

07 / Governance

三个让领导放心的管控点

Gate

没过挑战不让写

绿场要 grill-signoff approved；棕地先 reverse-signoff，再谈 To-Be 与改造。

Atomic

一次只做一个任务

单任务 + TDD。失败三次停下留痕，拒绝上下文膨胀。

Budget

人在环上，不在环里

每会话最多五个任务。handoff 续跑，或 touch .ralph-stop 急停。

10 / Decision ask

请领导确认三件事

  1. 以本 Skills 体系作为 AI 辅助研发的标准交付操作系统
  2. 新项目强制模块化 PRD 并过挑战门；老项目先 As-Is 忠实度签核再改造
  3. 批准下一阶段：Review 闸、表征测试基线、绞杀式 migrate 编排

目标不是替代工程判断，而是让判断发生在正确的关卡。
