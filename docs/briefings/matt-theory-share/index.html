场景 1 · 手头状态

全新项目：给到开发的需求，还不够 AI 直接落地

你大概有

口头想法、一页粗糙说明、原型截图，或「先做个类似某某的」。

你大概没有

模块边界、验收标准、非目标、关键决策。这些一缺，AI 只能猜。

实用判断：如果你不敢把当前文档直接交给另一个人独立交付，就还没到「能进实现」。

PRD 不明，就还不能进循环实现
可举 PulseNotes 或组内真实新品例子。

场景 1 · 常见坑

新品最容易怎么翻车

一把梭写码

「帮我全做完」：范围膨胀，做出来的也不是你想要的。

长文不挑战

一口气超长 PRD，歧义原样进代码。

没有共同词

同一概念三种叫法，AI 说话又长又飘。

错误起手
# 看起来很快
直接：「按这个想法把系统做出来」

# 实际发生
范围悄悄变大 · 验收对不上 · 返工比从零还贵
快开始，不等于快交付
请一人分享：最近一次「AI 写了很多但不可用」卡在哪。

场景 1 · 推荐路径

写清，挑战，再循环实现

1拷问对齐 + 领域词表CONTEXT / 决策
2合成模块化需求宏观 + 模块 PRD
3成品挑战（挑战门）签核 approved
4拆任务 + 测试先行小步做循环实现

编排入口：写需求 → 挑战门 → 循环实现。底下靠拷问、词表、测试驱动撑住。

/prd-author → /prd-grill → /prd-build-loop
点明：挑战门没过，实现循环应停。可 skip，但要显式记录。

场景 1 · 讨论

先把问题抛出去

题 A

你最近一个新品需求，卡在哪一层：目标、边界，还是验收？

题 B

如果只能多做一件事再让 AI 写码，你选「拷问对齐」还是「先写测试」？为什么？

先记着，后半场分组再答。分享人可以先示范自己的答案 30 秒。

场景 1 讨论题
示范方向：多数人选拷问；验收已经很清楚时，测试可以优先。

场景 2 · 手头状态

在建项目：已有部分功能，也有存量代码，要续接

你大概有

能跑的模块、半成品分支、零散文档或旧票、线上或联调环境。

真正麻烦在哪

「已实现 / 未实现 / 说了但没做」糊成一团。新需求往上叠，旧行为没人敢碰。

续接要接的是下一批变更。别假装从零重做一遍。

有代码，就先尊重现状
强调：这是团队最高频场景，比纯新品更常见。

场景 2 · 常见坑

续接时最贵的三种错法

当白板重写

新需求一来就「整体重做」，踩坏已上线行为。

只补两句需求

新旧边界对不齐，AI 在旧代码上乱接。

没有对照表

重复造轮子，或该改的漏改。

错误起手
# 常见一句话
「在现有项目上按新需求继续做」

# 缺了什么
已实现清单 · 不可破坏行为 · 本迭代目标态范围
续接不是绿场缩短版
问：你们更怕改坏旧功能，还是新功能接不上？

场景 2 · 推荐路径

摸清现状，钉住旧行为，只写清下一批目标态

1对照文档 / 票 / 代码，列出已交付与缺口现状表
2对改到的边界做表征（测试或关键路径清单）安全网
3只为下一批变更写模块化目标态续接 PRD
4挑战门通过后，再进循环实现 / 续跑过门

不必一上来全量逆向。但凡是要改的边界，都得说清「现在怎样、目标怎样」。

局部摸底 + 增量目标态 + 挑战门
文档与代码冲突时：以可验证行为为准，冲突记入未知清单。

场景 2 · 讨论

续接现场最想听的两问

题 A

「文档说有、代码没有」或反过来，你们最近一次是怎么发现的？

题 B

续接时你更怕改坏旧功能，还是新功能接不上？各自该先补什么产物？

场景 2 讨论题
引导：怕改坏就先表征；怕接不上就先补对照表和目标态范围。

场景 3 · 手头状态

老旧改造：缺需求说明、缺文档的历史项目

你大概有

能跑（或勉强能跑）的代码、口口相传、零星工单、生产上的「潜规则」。

你几乎没有

可信的需求说明、架构说明、验收基线。行为主要活在代码和人口里。

这类项目的第一目标通常不是「写得更快」，而是改完还认得自己。

没文档，也不等于可以瞎改
可点：重构、迁移、换皮、抽服务，起手式都是先忠实。

场景 3 · 常见坑

老改最容易踩的雷

整仓重构

「让 AI 重构整个项目」：暗逻辑漂移，线上事故。

现状当待办

把「现状描述」喂给实现循环，等于把现在当成目标。

不签核就改

忠实度没人认，改完才发现漏了分支逻辑。

铁律
现状  = 忠实描述「现在是什么」（As-Is）
目标态  = 明确「我们要改成什么」（To-Be）

禁止：只有现状文档就进入循环实现
现状描述不是实现待办
这是本场最硬的一条规则，收束时还要再说一遍。

场景 3 · 推荐路径

逆向，签核，表征，再定改造目标

1代码考古，产出模块化现状文档系统图 / 债务 / 未知
2忠实度签核reverse-signoff
3表征基线：关键行为钉成测试或清单安全网
4写目标态 / 迁移计划 → 挑战门 → 实现与后半段汇合

编排入口先是逆向，然后才是挑战与循环实现。前半段慢一点，后半段才敢加速。

/prd-reverse → 表征 → 目标态 → /prd-grill → /prd-build-loop
未知清单要公开：不知道的，比假装知道更安全。

场景 3 · 讨论

老改时最该对齐的两问

题 A

没文档时你更信：老员工口述、生产日志，还是代码？怎么交叉验证？

题 B

「先表征再改造」会不会太慢？你觉得慢在哪，省在哪？

场景 3 讨论题
引导：慢在前置，省在返工和事故；交叉验证至少两源一致。

收束
